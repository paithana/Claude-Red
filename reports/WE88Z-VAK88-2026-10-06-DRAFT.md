## Executive Summary

A penetration test was conducted against two gambling platform ecosystems: **Platform A** (Luxino/ZTech Dev multi-tenant SaaS: vak88z2, we88c, slxoz1688 tenants) and **Platform B** (Kaichon/CyberPlus PHP gambling stack: cybermagic555.com, cyberplusr9.com). The assessment identified **99 confirmed security findings** and **3 possible findings** spanning Critical through Info severity across both platforms.

Both platforms are critically compromised. Platform A exposes financial data for all operators and players through unauthenticated and over-privileged API endpoints. Platform B allows unauthenticated arbitrary credit injection via an unsigned LINE bot webhook, full database dumps via GTID-bypass SQLi, and exposes live mule bank credentials, plaintext owner passwords, and 2FA seeds through its own API responses.

### Platform A: Luxino/vak88z/we88c (FeathersJS + Go SaaS)

The platform uses a shared multi-tenant API infrastructure (`{TID}pbapi/mgapi/bgapi.asdgapicenterssdo.com`). Tenant isolation is enforced only by JWT `cf` claim — the BO admin endpoint (`/bo/info/admin`) ignores the `domain` parameter entirely and returns all 134 admin accounts to any valid player JWT. The `/pb/latest-win` and `/pb/latest-withdraw` endpoints are unauthenticated and return player `secret_key` credentials in the default response projection — no injection required; 50 keys per request from `/pb/latest-win` (F02, revised) and 10 per request from `/pb/latest-withdraw` (F103, revised from CWE-943 to CWE-200). A full LuxSMS APK interception infrastructure was mapped (F04), with 6 APK variants in publicly accessible GCS buckets.

**Go middleware crash**: All POST endpoints on mgapi/bgapi returned `401 Internal Server Error` due to a nil-pointer panic for much of the assessment period, blocking deposit creation and BO authentication. This limited live exploitation of deposit and approval flows.

### Platform B: Kaichon/CyberPlus (PHP monolith)

The Kaichon/CyberPlus platform shares a common PHP codebase across operators. The LINE bot webhook handler (`cmd/index.php`) performs no `X-Line-Signature` validation — any attacker who knows the hardcoded God user ID can grant themselves admin privileges and inject credits to any account (confirmed: 5,000 credits to `kc26`). The `LoginOwner` API response leaks the TOTP seed in plaintext, enabling 2FA bypass. `AddCredit` applies no authorization beyond an owner token, and was confirmed to inject 6,500 credits to a test account. Sequential IDOR on the Employee endpoint extracted 216 owner records including MySQL credentials (`vikingpro_root / vikingpro_cyberplus`). Two SQL injection vectors in `AddCreditBank` (CTE blind, time-blind) were confirmed, with WAF blocking error-based extraction.

## 2. Critical Findings

### F08: CORS Wildcard Configuration
**Severity:** Critical | **CVSS:** 9.1 | **CWE-942**

Both platforms return `Access-Control-Allow-Origin: *` with full Authorization header support, allowing any malicious website to make authenticated API calls if JWT is accessible.

**Impact:** Account takeover via XSS, credential theft from any origin.

**Evidence:**
```http
Access-Control-Allow-Origin: *
Access-Control-Allow-Headers: Content-Type, Authorization, ...
Access-Control-Allow-Methods: *
```

**Remediation:** Implement strict origin allowlist.

### F09: OTP Rate Limiting Missing
**Severity:** Critical | **CVSS:** 9.0 | **CWE-307**

OTP verification endpoint has no lockout after failed attempts. OTP request endpoint allows unlimited requests.

**Impact:** 
- OTP brute force (1M combinations, 3-minute window)
- SMS bombing/toll fraud

**Evidence:**
- 10+ rapid wrong OTP attempts: No lockout
- 5 rapid OTP requests: All succeeded with unique references

**Remediation:** Implement exponential backoff and account lockout.

### F02: Unauthenticated secret_key Mass Exposure via /pb/latest-win [REVISED]
**Severity:** High | **CVSS:** 7.5 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N) | **CWE-200**

`GET /pb/latest-win` is a public, unauthenticated endpoint that returns up to 50 recent game win records. Each record includes the player's `secret_key` (64-char hex) in the default response projection — no query manipulation required. The endpoint accepts the `$where` parameter without error, but re-testing confirms the parameter is currently **ignored** by the server (returning the same 50 records regardless of `$where=1===2` vs `$where=1===1`). The root vulnerability is an unconstrained response projection, not server-side JavaScript execution.

**Note (revised 2026-10-17):** Earlier session data appeared to show `$where` JS evaluation; controlled re-testing with definitive false conditions (`$where=1===2`, `$where=false`) confirms no filtering occurs. The CWE-943 (NoSQL Injection) classification has been removed. All secret_keys extracted were obtained from the default unauthenticated response, not via injected JS. CWE-200 is the correct classification.

**Vector:**
```bash
# No injection needed — secret_key in default response
GET https://{TID}pbapi.asdgapicenterssdo.com/pb/latest-win?domain=m.vak88z2.com

# $where accepted but ignored (server strips parameter)
GET .../pb/latest-win?domain=m.vak88z2.com&$where=1===2  # still returns 50 records
```

**Impact:**
- 50 unique player `secret_key` values exposed per unauthenticated request
- Combined with F67 (WSS broadcast), attacker can harvest secret_keys for all active players in real time
- secret_key is the HMAC signing credential for game-provider API calls (see F40 exploit chain)
- No injection, no auth, no rate-limit — trivially mass-harvested

**Evidence:** 50 secret_keys returned per unauthenticated GET; `$where=1===2` returns identical 50 records confirming no JS evaluation; secret_keys confirmed in F67 WSS broadcast and F40 game credit chain

### F03: Public Data Leak — /pb/latest-withdraw [CONFIRMED - MEDIUM]
**Tenant:** vak88z2, we88c, slxoz1688 | **CWE-200 (Information Exposure)** | **CVSS:** 5.3 (AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N)

`GET /pb/latest-withdraw` is a public, unauthenticated endpoint that returns the 10 most recent withdrawal records for a given domain. No authentication or rate-limiting is enforced. Records include withdrawal amounts, status, and timing — sufficient to infer platform cash-out volume and active player withdrawal patterns.

**Request:**
```
GET https://{TID}pbapi.asdgapicenterssdo.com/pb/latest-withdraw?domain=m.vak88z2.com
```

**Sample response fields (10 records per query):**
- `amount` — withdrawal amount in THB
- `status` — approval state (`approved`, `pending`, `rejected`)
- `created_at`, `updated_at` — timestamps
- `payment_type` — withdrawal method (bank transfer, TrueWallet)

**Impact:** Unauthenticated adversaries can continuously poll the endpoint to map platform liquidity, identify withdrawal approval latency, and build a timeline of cash-out activity across all tenants sharing the same domain suffix. No PII (names, account numbers) is included in this endpoint — those are in F36.

**Evidence:** 10 withdrawal records returned per unauthenticated request; confirmed across vak88z2, we88c tenants.

**Remediation:** Require player authentication on `/pb/latest-withdraw`; or strip amount/status fields from the public response if the endpoint must remain public.

### F119: BankSMS_IntercepterVX APK — SMS Intercept Malware Used as Payment Confirmation Relay [CONFIRMED - CRITICAL]

**Analysed:** 2026-10-23  
**Artifact:** `BankSMS_IntercepterVX.apk` (sha256: `31cd4540d4a387fa00774f01b44a3c6d13ac2687675cc4612d889571bec81b83`, 4.8 MB)  
**Evidence IDs:** `ev_ef4e5e59…` (parent), `ev_4d8bce98…` (onReceive), `ev_7e3536d3…` (EncodeStr), `ev_99ebce7a…` (onCreate), `ev_67d408d0…` (showAlert)  
**Method:** Static analysis via JADX headless MCP (REA); APK never executed.

#### Summary

`BankSMS_IntercepterVX.apk` is a purpose-built Android SMS-intercept relay. When installed on a mule's or operator's device, it silently captures inbound SCB and KBank payment-confirmation SMS messages and forwards the decrypted content to a configurable C2 HTTP endpoint. The app is the Android link in the vak88z2 deposit confirmation pipeline.

#### Manifest (static)

| Field | Value |
|-------|-------|
| Package | `com.example.otp` |
| Label | `BankSMS Intercepter` |
| Version | 1.0 (versionCode 1) |
| minSdk / targetSdk | 23 / 31 |
| Debuggable | `true` (debug build) |
| Permissions | `RECEIVE_SMS`, `INTERNET`, `FOREGROUND_SERVICE` |

#### Architecture

```
[SCB/KBank SMS] ──→ ReceiveSms.onReceive()
                        ├─ filter: sender == "027777777" (SCB) or "KBank"
                        ├─ dedup: LastBody static field
                        ├─ read SharedPrefs: Domain, BankNumber
                        ├─ build cleartext: BankType=SCB&Key=omg357159wtf&Body=<sms>&Token=<bank_acct>
                        ├─ Util.EncodeStr(plaintext, "omg357159wtf")
                        │     → SHA-256("omg357159wtf") as 32-byte AES key
                        │     → SecureRandom 16-byte IV (prepended)
                        │     → AES/CBC/PKCS5 encrypt
                        │     → Base64(NO_WRAP)
                        └─ POST https://{Domain}/api/CheckAmtBankVX
                               form field: Param=<base64_ciphertext>
```

#### Key findings

**[CONFIRMED] Hardcoded API key / encryption key:** `omg357159wtf`  
Used as both a query parameter value (`&Key=omg357159wtf`) and as the AES key derivation input (`SHA-256("omg357159wtf")`). Any party with this string can decrypt all intercepted SMS data in transit.

**[CONFIRMED] C2 endpoint:** `https://{Domain}/api/CheckAmtBankVX`  
`Domain` is runtime-configured via the operator UI (`editTextMessage` / SharedPreferences `"MyPrefs"` key `"Domain"`). No default domain is hardcoded. The prior probe dataset (`banksms_c2_probe.json`) shows `cybermagic555.com` and `cyberplusr9.com` both returned 404 on this endpoint at the time of probing — active C2 domain TBD.

**[CONFIRMED] Bank account as identity token:**  
`BankNumber` (SharedPreferences `"BankNumber"`) is sent as `&Token=<value>` — the C2 side correlates incoming SMS to a specific bank account by this token, enabling the platform to confirm deposits to multiple mule accounts from a single C2.

**[CONFIRMED] SMS filter — SCB + KBank only:**  
- Sender `"027777777"` → `BankType=SCB` (SCB's official SMS alphanumeric sender)  
- Sender `"KBank"` → `BankType=KBANK`  
- All other senders silently dropped — targeted precisely at the two banks confirmed in the settlement pool (F91: SCB and KBank mules).

**[CONFIRMED] Operator config UI (MainActivity):**  
The app presents two `EditText` fields (`editTextMessage` = Domain, `editTextMessage2` = BankNumber) pre-populated from SharedPreferences on launch. The "Save" button (`btnShowAlert`) writes both values and displays a confirmation dialog: `"Set your target Server to: {Domain} \n Set Bank Account to: {BankNumber}"`.
